## 1. System Classification

**System Type:** Extraction (intent classification + structured data resolution)

**Description:**
Real-time Shopify catalog intelligence for a customer support chat agent. Users ask about product availability, sizing, stock, and variant options. A hybrid intent classifier (keyword pre-filter + structured parsing) detects the type of catalog query, then resolves it against live product/stock data via the CatalogDataSource. No LLM calls for catalog queries. "Good" looks like: accurate variant matching, zero hallucinated stock data, graceful handling of ambiguous/out-of-stock/not-found cases.

**Critical Failure Modes:**
1. Hallucinating stock data — saying an item is in stock when it is not (blocking: violates CORE-01)
2. Missing or misclassifying a valid catalog intent — user asks about sizing and gets a generic response
3. Wrong variant match — user asks for "medium blue" and gets small black (customer frustration, returns)
4. Silent failure on ambiguous query — user gets a wrong answer instead of being asked to clarify

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** E-commerce / Shopify

**User Population:** Online shoppers interacting with a customer support chat agent on a Shopify store. Varied technical literacy, most familiar with natural product descriptions ("medium blue hoodie"). Includes repeat customers, first-time browsers, and mobile shoppers who expect fast, accurate answers without repeating themselves.

**Stakes Level:** High — wrong catalog information directly causes lost sales, returns, chargebacks, and eroded customer trust. Industry data shows 68% of consumers will not use a chatbot again after a single bad experience, and 58% abandon brands entirely after poor service (Adfinite 2026, citing STRYDE 2025 and Fullview 2025 reports). A single hallucinated stock claim can cost thousands in margin (Zoocx 2026). Product questions have only a ~45% chatbot resolution rate — nearly half of catalog queries currently fail.

**Output Consequence:** Catalog responses are presented as authoritative product information. If the agent says "in stock," the customer expects to purchase. If the agent matches the wrong variant, the customer receives the wrong item and initiates a return. If the agent claims a product has features it doesn't have, the store bears liability for the inaccurate claim. Under the FTC Act, AI-generated product claims are treated as company representations — the business is responsible for what the agent says.

### What Domain Experts Evaluate Against

**Dimension: Variant match precision**
Good (domain expert would accept): Correctly resolves "medium blue hoodie" to Size=Medium, Color=Blue within the correct product. Returns exact variant ID. Distinguishes between color shades ("navy" vs "royal blue").
Bad (domain expert would flag): Returns wrong variant (small black instead of medium blue). Says "we don't have that" when the variant exists. Collapses multiple color shades into one option.
Stakes: High
Source: E-commerce merchandising practice — wrong variant match causes returns (~20-40% of online returns are size/color related), exchange shipping costs, and customer frustration.

**Dimension: Stock accuracy**
Good (domain expert would accept): Reports real-time stock status from live inventory source. Correctly distinguishes in-stock, low-stock (≤5 units), out-of-stock, and backordered. Shows urgency flag for low-stock items ("Only 2 left!").
Bad (domain expert would flag): Says in stock when actually out of stock. Recommends an out-of-stock product as available. Uses cached stock data. Omits stock status entirely.
Stakes: Critical
Source: Track 4 mandate (CORE-01). Zoocx 2026 — "phantom product recommendation" failure case: bot says XL is available when it's been OOS for months.

**Dimension: Intent classification fidelity**
Good (domain expert would accept): Correctly identifies query as stock check vs sizing inquiry vs product search vs variant lookup. Rejects order/return/refund queries without false-positive catalog matches. Handles multi-part queries ("Do you have this in medium and is it in stock?").
Bad (domain expert would flag): Misclassifies a sizing question as general search. Matches "when will my order ship?" to product_search because "ship" matches a keyword. Fails to detect a clear stock check from "how many left."
Stakes: Medium
Source: Practitioner knowledge — Adfinite 2026 reports 29% of chatbot failures trace to poor intent recognition.

**Dimension: Ambiguity resolution**
Good (domain expert would accept): Asks a specific clarifying question when the query is ambiguous ("We have the Classic Hoodie in Blue in Small, Medium, and Large. Which size?"). Distinguishes between missing product info (no match) and unresolved variant options (partial match).
Bad (domain expert would flag): Picks an arbitrary match without asking. Displays "we have that in blue" when the user needs a specific size. Remains silent about uncertainty. Forces the customer to repeat themselves.
Stakes: High
Source: UX research — Adfinite 2026: "silent partial match" where bot returns any match without confirming is a top failure mode. 52% of customers list "bot misunderstanding my question" as the worst chatbot issue.

**Dimension: Not-found handling with alternatives**
Good (domain expert would accept): Gracefully states the item is unavailable. Offers up to 5 alternatives from the same category within ±20% price range. Alternatives feel helpful, not pushy. No dead-end responses.
Bad (domain expert would flag): Ignores the query. Returns an irrelevant result. Gives no follow-up options. Says "we don't have that" with no alternative. Takes an obviously wrong guess.
Stakes: Medium
Source: E-commerce conversion optimization — alternative suggestions recover 10-15% of otherwise lost sales. D-09 and D-10 from CONTEXT.md.

**Dimension: Stock data recency**
Good (domain expert would accept): Every stock query fetches fresh data from the inventory source. Never serves cached stock data. If the data source is unreachable, returns "stock data temporarily unavailable" instead of a stale value.
Bad (domain expert would flag): Uses 2-minute-old stock data. Serves "in stock" for an item that sold out seconds ago. Falls back to cached values when the API errors. Masks data freshness issues.
Stakes: Critical
Source: STATE.md locked decision (stock NEVER cached). Zoocx 2026 Root Cause 2: "No Access to Real-Time Data" — stale data is a hallucination waiting to happen.

**Dimension: Epistemic honesty / uncertainty expression**
Good (domain expert would accept): Clearly distinguishes between what it knows with certainty (from live data) and what it is estimating. If no exact match, communicates the gap explicitly: "We don't have a blue hoodie in Small, but we have it in Medium and Large."
Bad (domain expert would flag): Sounds equally confident whether the answer is grounded in live data or generated from general patterns. Never expresses uncertainty. Makes up plausible-sounding but unverifiable product claims. Refuses to say "I don't know."
Stakes: High
Source: Zoocx 2026 — "epistemic honesty is a meaningful signal about the quality of the underlying system." Adfinite 2026 — AI chatbots hallucinate 2.5% to 22.4% of the time without proper grounding.

### Known Failure Modes in This Domain

1. **The synonym gap** — Customer says "navy blue oatmeal hoodie" but the system only matches "Blue/Oatmeal/Hoodie" if synonym layers are complete. If "oatmeal" isn't in the color synonym table, the option is silently dropped.
2. **The partial-variant trap** — "Do you have small hoodies?" — matches size but not color. System should show all small hoodie variants instead of guessing a color.
3. **The multi-stop query** — "What about the large one in green?" — requires conversation state from the prior turn. If context expired or wasn't stored, the system has no product to attach options to.
4. **Cached catalog, stale availability** — Catalog cached at 2-min TTL, but stock should never be cached (per STATE.md decisions). A product sold out within the TTL window still shows as available.
5. **The hallucinated feature** — Bot claims a product has a feature, material, or specification that doesn't exist in the live catalog. Common with general-purpose AI that fills knowledge gaps from training data rather than store data (Zoocx 2026 — "the phantom product recommendation").
6. **The silent variant collapse** — "Blue hoodie" matches one blue variant and returns it as the only option, but the product actually comes in multiple blue shades (navy, sky, royal). Customer never sees the other options because the system collapsed variants silently.

## 3. Implementation Pattern: Hybrid Intent Classifier

> No external AI framework selected. Intent classification uses a hybrid keyword + structured parsing pattern that mirrors the existing OffTopicDetector but is significantly more layered because catalog queries require product/variant resolution, not just topic classification. See `src/services/offTopicDetector.ts` for the established class pattern.

### Intent Catalog

The system detects exactly four intent types, each with distinct matching rules:

| Intent | Trigger Keywords | Example | Resolution Path |
|--------|-----------------|---------|-----------------|
| `stock_check` | `stock`, `available`, `in stock`, `backorder`, `restock`, `back in stock`, `inventory` | "Is the blue hoodie in stock?" | Variant lookup → StockInfo check |
| `sizing_inquiry` | `size`, `sizing`, `fit`, `measurement`, `dimension`, `small`, `medium`, `large` (when catalog context) | "Does this come in medium?" | Product lookup → Option values for Size |
| `product_search` | `have`, `carry`, `sell`, `product`, `looking for`, `got any` + product terms | "Do you carry winter jackets?" | Full-text search across title + type + description |
| `variant_lookup` | Product name + option combination (detected by structured parser) | "Medium blue classic hoodie" | Product match → option value resolution → exact variant |

### Keyword Pre-Filter Design (False-Positive Avoidance)

The keyword pre-filter follows a three-layer design to avoid false positives from overlapping domains (orders, returns, exchanges):

```
Layer 1: Intent-specific inclusion sets
  └─ Each intent has its OWN keyword map (not one big list)
  └─ Query must match ≥1 keyword from ONE intent group to trigger

Layer 2: Exclusion guards per intent group
  └─ stock_check EXCLUDES: 'refund', 'return', 'exchange', 'order status', 'tracking'
  └─ sizing_inquiry EXCLUDES: 'refund', 'return', 'exchange', 'cancel'
  └─ If inclusion AND exclusion match → confidence penalty (-0.3)

Layer 3: Intersection with ON_TOPIC_KEYWORDS
  └─ CatalogKeywordChecker runs AFTER OffTopicDetector
  └─ If OffTopicDetector flagged as off-topic → skip catalog check entirely
```

```typescript
// Layer 1 + 2: Intent-specific keyword maps with exclusion guards
const STOCK_CHECK_KEYWORDS: KeywordGroup = {
  includes: ['stock', 'available', 'in stock', 'backorder', 'restock',
             'back in stock', 'inventory', 'how many', 'still have'],
  excludes: ['refund', 'return', 'exchange', 'order status', 'tracking',
             'cancel', 'price match', 'coupon'],
  weight: 1.0,
};

const SIZING_INQUIRY_KEYWORDS: KeywordGroup = {
  includes: ['size', 'sizing', 'fit', 'measurement', 'dimension',
             'small', 'medium', 'large', 'extra large', 'x-large',
             'xl', 'xxl', 'how does it fit', 'true to size'],
  excludes: ['refund', 'return', 'exchange', 'cancel', 'order status'],
  weight: 1.0,
};

const PRODUCT_SEARCH_KEYWORDS: KeywordGroup = {
  includes: ['have', 'carry', 'sell', 'product', 'looking for', 'got any',
             'do you', 'can i get', 'is there', 'offer'],
  excludes: ['refund', 'return', 'exchange', 'order', 'tracking', 'cancel',
             'price match', 'coupon', 'discount'],
  weight: 0.7,  // lower weight — more prone to false positives
};
```

**False-positive defense: On-topic intersection check**

```typescript
function isCatalogQuery(query: string): boolean {
  // Must not be off-topic first (OffTopicDetector gate)
  // Then must match at least one intent group
  // Then must NOT have more exclusion hits than inclusion hits
  for (const [intent, group] of Object.entries(INTENT_GROUPS)) {
    const includeCount = countMatches(query, group.includes);
    const excludeCount = countMatches(query, group.excludes);
    if (includeCount > 0 && includeCount > excludeCount) {
      return true;  // inclusion beats exclusion
    }
  }
  return false;
}
```

### Structured Parsing Pipeline

The structured parser runs after keyword pre-filter confirms catalog intent. It operates in three sequential phases — each phase narrows the candidate set:

```
PHASE 1: Product Match
  └─ Tokenize query into noun phrases
  └─ Match each token against known product titles and types
  └─ Use sliding window (2-4 tokens) for multi-word product names
  └─ Result: candidate product(s) or null

PHASE 2: Option Value Extraction  
  └─ Scan remaining tokens not consumed by product match
  └─ Check against synonym tables (size → normalized, color → canonical)
  └─ Extract known option keys: Size, Color, Material
  └─ Result: map of { optionName: normalizedValue }

PHASE 3: Variant Resolution
  └─ If product AND all option values match → exact variant
  └─ If product + partial option values → list matching variants
  └─ If product only → show all variants grouped by options
  └─ If no product match → full-text search
```

```typescript
// Phase 1: Product matching via token sliding window
function matchProduct(query: string, products: Product[]): ProductMatch {
  const tokens = tokenize(query);  // ['medium', 'blue', 'classic', 'hoodie']
  
  for (let windowSize = 4; windowSize >= 2; windowSize--) {
    for (let i = 0; i <= tokens.length - windowSize; i++) {
      const phrase = tokens.slice(i, i + windowSize).join(' ');
      const product = findProductByTitle(phrase, products);
      if (product) {
        return {
          product,
          consumedTokens: tokens.slice(i, i + windowSize),
          remainingTokens: [...tokens.slice(0, i), ...tokens.slice(i + windowSize)],
        };
      }
    }
  }
  return null;  // no direct product match
}

// Phase 2: Extract option values from remaining tokens
function extractOptions(
  tokens: string[],
  synonymTables: SynonymTables
): Record<string, string> {
  const options: Record<string, string> = {};
  
  // Priority order: Size → Color → Material (most discriminative first)
  for (const token of tokens) {
    const normalizedSize = synonymTables.size.normalize(token);
    if (normalizedSize) { options.Size = normalizedSize; continue; }
    
    const normalizedColor = synonymTables.color.normalize(token);
    if (normalizedColor) { options.Color = normalizedColor; continue; }
    
    const normalizedMaterial = synonymTables.material.normalize(token);
    if (normalizedMaterial) { options.Material = normalizedMaterial; continue; }
  }
  
  return options;
}

// Phase 3: Variant resolution with partial match handling
function resolveVariant(
  product: Product,
  options: Record<string, string>
): VariantResolution {
  const exactMatch = product.variants.find(v =>
    Object.entries(options).every(([key, val]) => v.options[key] === val)
  );
  
  if (exactMatch) {
    return { type: 'exact', variant: exactMatch, product };
  }
  
  if (Object.keys(options).length > 0) {
    // Partial match — return all variants matching known options
    const partialMatches = product.variants.filter(v =>
      Object.entries(options).some(([key, val]) => v.options[key] === val)
    );
    return { type: 'partial', options, product, candidates: partialMatches };
  }
  
  // No options specified — return all variants
  return { type: 'product_only', product, variants: product.variants };
}
```

### Cross-Turn Catalog Query Handling

Cross-turn queries ("What about the large one?", "How about in green?") require context from the previous turn. The system uses an explicit conversation context structure:

```typescript
interface CatalogConversationContext {
  lastIntent: CatalogIntent | null;
  lastProduct: Product | null;
  lastOptions: Record<string, string>;       // options from previous turn
  unmappedOptions: Record<string, string>;   // options mentioned but not resolved
  turnNumber: number;
  expiresAt: number;                          // timestamp — stale after 5 min or 3 turns
}

// Context expiry: 5 minutes OR 3 turns, whichever comes first
const CONTEXT_TTL_MS = 5 * 60 * 1000;
const CONTEXT_MAX_TURNS = 3;
```

**Resolution strategy for cross-turn queries:**
1. Check if current query contains product terms → if yes, this is a new query (reset context)
2. Check if current query contains option values only (no product) → merge with last context
3. Check if current query is a pronoun/anaphora ("it", "that", "the one") → fill from `lastProduct`
4. Context expired → ask for clarification ("Which product were you asking about?")

```typescript
function resolveWithContext(
  query: string,
  context: CatalogConversationContext,
  products: Product[]
): ResolvedQuery {
  const hasProductTerms = containsProductTerms(query, products);
  const hasOptionValues = containsOptionValues(query, SYNONYM_TABLES);
  
  if (hasProductTerms) {
    // Fresh query — reset context
    return resolveFreshQuery(query, products);
  }
  
  if (contextExpired(context)) {
    return { type: 'context_expired', message: 'Which product were you asking about?' };
  }
  
  // Cross-turn resolution
  const options = extractOptions(tokenize(query), SYNONYM_TABLES);
  const fullOptions = { ...context.lastOptions, ...options };  // new options override old
  
  if (context.lastProduct) {
    return resolveVariantOnProduct(context.lastProduct, fullOptions);
  }
  
  // No context to work with
  return { type: 'ambiguous', message: 'Which product are you asking about?' };
}
```

| Concept | What It Is | When You Use It |

### Common Pitfalls

1. **Over-matching keywords across domains** — "Do you have any idea when my order will ship?" contains "have" which matches `PRODUCT_SEARCH_KEYWORDS.includes`. **Mitigation:** Every intent group has its own exclusion list. If `order`, `ship`, `tracking` appear more than catalog terms, the keyword pre-filter rejects the match.

2. **Color synonym explosion** — Adding too many color synonyms increases maintenance burden and creates false matches (e.g., "rose" could be a color or a product type). **Rule:** Only add a synonym when a real user query requires it. Start with 6-8 canonical colors, each with 3-5 common aliases.

3. **Partial queries without context** — "What about the large one?" fails if conversation context is empty. **Check:** Always check `CatalogConversationContext` expiry before attempting cross-turn resolution. If expired, ask for clarification rather than guessing.

4. **Silent partial match** — User asks "blue hoodie" and system returns any blue variant without confirming the product. **Mitigation:** Distinguish `type: 'partial'` from `type: 'exact'` in the result. Partial matches must include a clarifying response: "We have the Classic Hoodie in Blue in Small, Medium, and Large. Which size?"

5. **Cached catalog, fresh stock inconsistency** — Catalog cached at 2-min TTL, but stock is live. After a "How many left?" query followed by "What about the other color?", the catalog may be stale. **Mitigation:** Always re-fetch stock data per query. Cache product metadata only (title, price range, options).

## 4. Implementation Guidance

**No LLM Calls in This Phase:**
The CatalogIntentDetector uses deterministic pattern matching end-to-end. Every catalog response is grounded in live (mock) data with zero LLM involvement. If a downstream phase introduces LLM-powered product recommendations, that will be documented in its own AI-SPEC.

### Core Pattern: Data Flow Pipeline

```
User message ──► OffTopicDetector ──► CatalogIntentDetector ──► CatalogService ──► Response Grounder
                    (Phase 2)                (keyword +                (data access +    (Phase 2 - enhanced
                                             structured parsing)        variant resolve)  for catalog routing)
```

**Step by step flow:**

1. **ChatWidget receives message** → calls `_generateAgentResponse(text)`
2. **OffTopicDetector check** — If off-topic, return refusal (existing Phase 2 logic)
3. **CatalogIntentDetector.detect(query, context?)**
   - Layer 1: Keyword pre-filter against 3 intent groups with exclusion guards
   - If no catalog intent → pass through to existing mock response logic
   - Layer 2: Cross-turn context resolution (merge with `CatalogConversationContext` if available)
   - Layer 3: Structured parsing (product match → option extraction → variant resolution)
   - Returns discriminated union `ResolvedQuery` type
4. **If catalog intent detected → CatalogService handles resolution:**
   - `loadProducts()` from `CatalogDataSource` (cached 2-min TTL)
   - `searchProducts(query)` — full-text search across title + type + description
   - `resolveVariant(product, options)` — exact/partial/no match
   - `checkStock(variant)` — always live, never cached
5. **Response is formatted** — product cards, stock badges, clarifying questions
6. **ResponseGrounder validates** — checks response against catalog data, flags any hallucination (extended from Phase 2)

### Conversation Context Management

Cross-turn catalog queries require explicit context propagation:

```typescript
// src/services/conversationContext.ts
class ConversationContextManager {
  private catalogContext: CatalogConversationContext | null = null;

  getCatalogContext(): CatalogConversationContext | null {
    if (this.catalogContext && Date.now() < this.catalogContext.expiresAt) {
      return this.catalogContext;
    }
    return null;  // expired — treat as fresh query
  }

  updateCatalogContext(result: ResolvedQuery): void {
    const lastProduct = extractProduct(result);
    const lastOptions = extractOptions(result);
    
    this.catalogContext = {
      lastIntent: result.type === 'not_catalog' ? null : result.intent,
      lastProduct,
      lastOptions,
      unmappedOptions: extractUnmapped(result),
      turnNumber: (this.catalogContext?.turnNumber ?? 0) + 1,
      expiresAt: Date.now() + 5 * 60 * 1000,
    };
  }

  clearCatalogContext(): void {
    this.catalogContext = null;
  }
}
```

**Context rules:**
- Context lives in the ChatWidget instance (browser-side, per-session)
- Expires after 5 minutes of inactivity OR 3 turns without product reference
- New query with product terms resets context entirely
- Pronoun/anaphora resolution ("it", "that", "the one") consumes `lastProduct`

## 4b. AI Systems Best Practices

> Cross-cutting patterns applied to deterministic catalog intent classification. Since Phase 3 uses no LLM, these cover structured output contracts, async data access, pipeline design discipline, context window management for conversations, and cost/latency budgeting for a zero-LLM system.

### 4b.1 Structured Outputs with Discriminated Unions

No Pydantic needed — TypeScript discriminated unions serve as the structured output contract. Every consumer must narrow on `type` before accessing fields. This eliminates "undefined check" bugs that plague optional-field interfaces.

```typescript
// GOOD: Discriminated union — all cases explicit, no undefined checks
type CatalogResponse =
  | { type: 'exact'; product: Product; variant: Variant; stock: StockInfo }
  | { type: 'partial'; product: Product; matchedOptions: Record<string, string>;
      unmatched: string[]; candidates: Variant[] }
  | { type: 'product_only'; product: Product; variants: Variant[] }
  | { type: 'search_results'; query: string; results: Product[]; totalCount: number }
  | { type: 'ambiguous'; message: string; clarification: AmbiguityInfo }
  | { type: 'not_found'; message: string; suggestions: Product[] }
  | { type: 'context_expired'; message: string }
  | { type: 'not_catalog' };

// BAD: Optional-field interface — every consumer must check for undefined
// interface CatalogResponse {
//   product?: Product;
//   variant?: Variant;
//   candidates?: Variant[];
//   // ... 5 more optional fields, all of which could be undefined
// }

// Consumer example — type narrowing guarantees safety
function formatResponse(response: CatalogResponse): string {
  switch (response.type) {
    case 'exact':
      return `**${response.product.title}** — ${response.variant.title} — ${
        response.stock.available ? 'In Stock' : 'Out of Stock'
      }`;
    case 'partial': {
      const options = Object.entries(response.matchedOptions)
        .map(([k, v]) => `${k}: ${v}`).join(', ');
      return `We have ${response.product.title} in ${options}. ` +
        `Available options: ${response.candidates.map(v => v.title).join(', ')}. Which one?`;
    }
    case 'ambiguous':
      return response.message;  // clarifying question shown as-is
    case 'not_found':
      return response.suggestions.length > 0
        ? `We don't carry that. Here are some similar options: ${response.suggestions.map(p => p.title).join(', ')}`
        : "Sorry, we don't have anything like that.";
    case 'not_catalog':
      return '';  // caller will fall through to non-catalog response pipeline
  }
}
```

**Validation: TypeScript type guards for runtime safety**

Even though the system is deterministic, add a runtime type guard to catch programming errors in the pipeline:

```typescript
function isValidCatalogResponse(obj: unknown): obj is CatalogResponse {
  if (typeof obj !== 'object' || obj === null) return false;
  const r = obj as Record<string, unknown>;
  if (typeof r.type !== 'string') return false;

  switch (r.type) {
    case 'exact':
      return 'product' in r && 'variant' in r && 'stock' in r;
    case 'partial':
      return 'product' in r && 'matchedOptions' in r && 'candidates' in r;
    case 'not_found':
      return 'suggestions' in r;
    case 'not_catalog':
      return true;
    default:
      return false;
  }
}
```

**Retry logic (for the pipeline, not an LLM):** If `isValidCatalogResponse` returns false (should never happen in production), log a structured error with the response data, increment `pipeline_error` counter, and return `{ type: 'not_found', message: "I couldn't find that product." }`.

### 4b.2 Async-First Design

The CatalogIntentDetector pipeline is mostly synchronous (pattern matching, string parsing), but data access (CatalogDataSource.loadProducts) is async. Design async boundaries carefully:

```typescript
// src/services/catalogService.ts
export class CatalogService {
  constructor(private dataSource: CatalogDataSource) {}

  // CORRECT: Public methods are async, load products then search locally
  async searchProducts(query: string): Promise<Product[]> {
    const products = await this.dataSource.loadProducts();  // single async call
    return this._localSearch(products, query);               // synchronous filtering
  }

  // CORRECT: Stock check is always fresh (never cached) — parallel fetch if multi-variant
  async checkMultiStock(variants: Variant[]): Promise<Map<string, StockInfo>> {
    const results = await Promise.all(                       // parallel — faster than sequential
      variants.map(v => this.dataSource.fetchStock(v.id))
    );
    return new Map(variants.map((v, i) => [v.id, results[i]]));
  }
}
```

**Common mistake: Sequential awaits for independent data**
```typescript
// BAD — sequential (each waits for previous)
const products = await this.dataSource.loadProducts();
const policies = await policyService.getAll();

// GOOD — parallel (both fire at once)
const [products, policies] = await Promise.all([
  this.dataSource.loadProducts(),
  policyService.getAll(),
]);
```

**Stream vs. await:** Not applicable for this deterministic system — there is no streaming output. All catalog responses are fully assembled before being sent to the user. For the conversation context manager, synchronous operations are fine (it's an in-memory data structure with no I/O).

### 4b.3 Pipeline Engineering Discipline

For deterministic intent classification systems, "prompt engineering" becomes **pipeline engineering** — how you design the keyword maps, parsing order, and fallback chains.

**System vs. User prompt separation (for deterministic systems):**

| Concept | Equivalent in Pipeline Engineering |
|---------|-----------------------------------|
| System prompt | Keyword maps + intent group definitions + synonym tables |
| User message | Raw query string input |
| Few-shot examples | Golden test cases in the test suite |
| Temperature / sampling | Confidence thresholds per intent group |
| Output format instruction | Discriminated union return type |

**Keyword sensitivity tuning (the deterministic version of prompt tuning):**

```typescript
// src/config/intent-thresholds.ts
export const INTENT_THRESHOLDS = {
  stock_check: {
    minKeywordMatches: 1,
    exclusionPenalty: 0.3,    // subtract if exclusion matches exceed inclusion
  },
  sizing_inquiry: {
    minKeywordMatches: 1,
    exclusionPenalty: 0.4,    // stricter — sizing gets misclassified more often
  },
  product_search: {
    minKeywordMatches: 2,     // needs 2+ keyword hits to avoid false positives
    exclusionPenalty: 0.5,    // highest penalty — most prone to over-matching
  },
} as const;
```

**Test-driven pipeline tuning:**
- Each keyword addition must be paired with a test case (the query that prompted the addition)
- Each keyword addition must also add a negative test case (a query that should NOT match)
- Golden test suite runs on every change to keyword maps or synonym tables
- No keyword/synonym change is committed without passing the full test suite

```typescript
// catalogIntentDetector.test.ts — example test structure
describe('CatalogIntentDetector', () => {
  describe('stock_check intent', () => {
    it('detects stock queries ("is the blue hoodie in stock?")', () => {
      expect(detect('is the blue hoodie in stock?').type).toBe('exact');
    });

    it('rejects order-status queries ("when will my order ship?")', () => {
      expect(detect("when will my order ship?").type).toBe('not_catalog');
    });

    it('rejects refund queries with stock keywords ("I want to return my order, has it been restocked?")', () => {
      const result = detect("I want to return my order, has it been restocked?");
      expect(result.type).toBe('not_catalog');  // "return" in exclusion list
    });
  });

  describe('cross-turn resolution', () => {
    it('uses last product for "What about large?" after hoodie query', () => {
      const firstTurn = detect("tell me about the classic hoodie");
      const context = buildContext(firstTurn);
      const secondTurn = detect("What about large?", context);
      expect(secondTurn.type).toBe('partial');
      if (secondTurn.type === 'partial') {
        expect(secondTurn.product.title.toLowerCase()).toContain('hoodie');
      }
    });
  });
});
```

**Set `max_tokens` equivalent:** In a deterministic system, this corresponds to pipeline depth limits — the structured parser should not attempt more than 3 passes (product → options → variant). If no match after 3 passes, return `not_found`.

### 4b.4 Context Window Management

For catalog conversation systems, the "context window" is the conversation turns available for cross-turn resolution, not an LLM token budget. Manage it with strict expiration and explicit boundaries.

**Catalog context expiry rules:**

```
┌──────────────────────────────────────────────┐
│  CatalogConversationContext                  │
│                                              │
│  Fields:                                     │
│  ├─ lastIntent: CatalogIntent | null         │
│  ├─ lastProduct: Product | null              │
│  ├─ lastOptions: Record<string, string>      │
│  ├─ unmappedOptions: string[]                │
│  ├─ turnNumber: number                       │
│  └─ expiresAt: timestamp (5min TTL)          │
│                                              │
│  Expiry conditions:                          │
│  ├─ Timeout: expiresAt < Date.now()          │
│  ├─ Turns: turnNumber >= CONTEXT_MAX_TURNS   │
│  └─ Reset: new product terms in query        │
└──────────────────────────────────────────────┘
```

**Summarization patterns (not for LLM, for context compaction):**

When the conversation context holds too many unmapped options across turns, compact them:

```typescript
// Compaction rule: If options from turn N have been overridden by turn N+1,
// discard the old ones. Keep only the latest option per dimension.
function compactContext(context: CatalogConversationContext): CatalogConversationContext {
  // Options from later turns override earlier ones
  // Unmapped tokens older than 1 turn are discarded
  return {
    ...context,
    unmappedOptions: context.turnNumber > 0 ? [] : context.unmappedOptions,
  };
}
```

**Cache invalidation strategy:**
- Product catalog cache: 2-min TTL. On write (admin updates catalog), invalidate immediately. Since this is a support agent (read-only), cache invalidation on write is optional — stale catalog metadata is acceptable within 2 minutes.
- Stock cache: NEVER. Every stock query hits the data source.
- Synonym table cache: Never needs invalidation — static config, versioned with code.

### 4b.5 Cost and Latency Budget

Since there are zero LLM calls in this phase, the cost is dominated by compute time and data source calls. No token costs.

**Per-query cost breakdown:**

| Pipeline Step | Latency Target | Cost | Cache Strategy |
|--------------|---------------|------|----------------|
| Keyword pre-filter | <1ms | $0 | Static keyword map |
| Cross-turn context merge | <1ms | $0 | In-memory Map |
| Structured parsing (3 phases) | <5ms | $0 | Pure computation |
| Product full-text search | <10ms | $0 | In-memory index on cached products |
| Stock data fetch | <100ms | $0 | Never cached (but free for mock data) |
| Response formatting | <2ms | $0 | Template string |
| **Total pipeline** | **<200ms** | **$0** | — |

**Caching strategy:**
```typescript
// src/services/cacheManager.ts
interface CacheEntry<T> {
  data: T;
  expiresAt: number;
}

class CacheManager {
  // Uses WeakRef if available, otherwise Map with TTL
  private store = new Map<string, CacheEntry<unknown>>();

  get<T>(key: string): T | null {
    const entry = this.store.get(key);
    if (entry && entry.expiresAt > Date.now()) return entry.data as T;
    this.store.delete(key);
    return null;
  }

  set<T>(key: string, data: T, ttlMs: number): void {
    this.store.set(key, { data, expiresAt: Date.now() + ttlMs });
  }

  // Exact-match cache for product lookups (key: product.title.toLowerCase())
  // Semantic similarity not needed — all matching is deterministic string comparison
}
```

**Alert thresholds for production:**
- Pipeline latency >500ms → log with query fingerprint, monitor for trend
- Stock fetch failure → retry once after 500ms, then return "stock data temporarily unavailable" instead of guessing
- Keyword false-positive rate >5% → flag for review (measured by user re-asking the same query in the next turn)

**Exact-match caching vs. semantic caching:**
- Use exact-match cache only (Map keyed on lowercase query text)
- Semantic caching (embedding-based) is overkill for this phase — all matching is deterministic and string-based
- If you see repeated identical queries from the same session (user clicking a suggested question), the exact-match cache avoids redundant parsing

| Pipeline latency (P50/P95/P99) | End-to-end catalog query resolution time | `performance.now()` wrapped around pipeline → aggregate in log aggregator | P95 > 300ms (warn), P95 > 500ms (critical) |
| Catalog hit & miss rate | % of queries classified as catalog intent → successfully resolved vs. ambiguous/not-found | Counter per `resolutionType` → percentage over sliding 1-hour window | Hit rate < 70% → flag for review |
| Stock fetch failure rate | % of stock checks that throw or timeout | try/catch counter on `fetchStock()` / total stock checks | > 2% (warn), > 5% (critical — data source may be down) |
| Ambiguous query rate | % of catalog queries returning `ambiguous` or `partial` | Counter per `ambiguous = true` / total catalog queries | > 25% → audit synonym tables and keyword maps |
| Cross-turn context usage | % of catalog queries that successfully use conversation context vs. start fresh | `contextUsed` boolean counter | < 10% → context expiry may be too aggressive |
| Intent false-positive rate | % of catalog-triggered queries where user's next response signals confusion | Manual signal: user rephrases, says "no", or escalates within next 2 turns | > 5% → audit exclusion guards and keyword thresholds |

### Alert Thresholds

| Condition | Severity | Response |
|-----------|----------|----------|
| Pipeline P95 latency > 500ms for 5+ min | Critical | Investigate CatalogDataSource response time. Check product cache hit rate. Consider increasing catalog cache TTL. |
| Stock fetch failure rate > 5% in any 10-min window | Critical | Check Shopify API health / mock data source availability. Switch to degraded mode (omit stock badges, state "stock data unavailable"). |
| Type guard validation failure (any) | Critical | Immediate engineering investigation — deterministic system should never produce invalid responses. |
| Intent false-positive rate > 5% in 4-hour window | High | Review last 50 false-positive queries. Add as negative test cases. Tune exclusion keyword maps. |
| Ambiguous query rate > 25% in 1-hour window | High | Catalog synonym tables may be missing common terms. Review color/size alias coverage. Check for new product additions not in synonym tables. |

### Smart Sampling Strategy

| Signal | Sample Rate | Review Method | Purpose |
|--------|------------|---------------|---------|
| User re-asks or rephrases (within 2 turns of catalog response) | 100% | Human review of conversation pair | Detects intent misclassification, poor ambiguity handling, or wrong variant match |
| Pipeline error or type guard failure | 100% | Immediate engineering review (alert-driven) | Catches programming bugs before they cascade |
| `type: 'ambiguous'` followed by user correcting or clarifying | 50% | Human review of ambiguity quality | Evaluates if clarifying question was specific enough; feeds synonym table improvements |
| Cross-turn query that resolves correctly | 10% | Automated log review (check `contextUsed: true` + `resolutionType !== 'ambiguous'`) | Validates context expiry and merge logic in production |
| Completely first-purchase session (no prior context) | 5% | Random human review | General quality signal for fresh queries without context assistance |
| Latency outlier (P99 > 1000ms) | 100% | Automated alert + log analysis | Identifies slow data sources, cache misses, or unexpected pipeline paths |
